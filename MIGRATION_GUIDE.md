# Руководство по миграции на новую систему ролей

## Обзор изменений

Проект был полностью отрефакторен с заменой роли `admin` на новую иерархию ролей:
- **Owner (Владелец)** - высший уровень
- **Director (Директор)** - второй уровень
- **Supervisor (Супервайзер)** - третий уровень (заменяет старую роль `admin`)
- **Manager (Менеджер)** - базовый уровень

## Миграции базы данных

### 1. Миграция 019: Добавление новых ролей
- Обновляет CHECK constraint для таблицы `users`
- Добавляет роли: `owner`, `director`, `supervisor`
- Удаляет роль `admin` из допустимых значений

### 2. Миграция 020: Миграция существующих данных
- Автоматически обновляет всех пользователей с ролью `admin` на `supervisor`
- Обеспечивает обратную совместимость

**Важно:** Выполните обе миграции в порядке их номеров!

## Изменения в конфигурации

### Переменные окружения (.env)

**Старые переменные (устарели, но поддерживаются для обратной совместимости):**
```
ADMIN_IDS=123456,789012  # Теперь назначает роль supervisor
```

**Новые переменные:**
```
OWNER_IDS=123456         # Telegram ID владельца (только через конфиг)
DIRECTOR_IDS=789012      # Telegram ID директоров (только для начальной настройки)
SUPERVISOR_IDS=345678    # Telegram ID супервайзеров (только для начальной настройки)
```

### Приоритет назначения ролей:
1. `OWNER_IDS` - высший приоритет, всегда обновляет роль на `owner`
2. `DIRECTOR_IDS` - назначает `director` только если пользователь еще `manager`
3. `SUPERVISOR_IDS` или `ADMIN_IDS` - назначает `supervisor` только если пользователь еще `manager`

## Изменения в API

### Обновленные зависимости:
- `get_admin_user()` → `get_supervisor_user()` (legacy alias сохранен)
- Добавлены: `get_director_user()`, `get_owner_user()`

### Обновленные проверки ролей:
- `user['role'] != 'admin'` → `user['role'] not in ('supervisor', 'director', 'owner')`
- `user['role'] == 'admin'` → `user['role'] in ('supervisor', 'director', 'owner')`

### Новые endpoints:
- `GET /api/admin/directors` - список директоров (только для owner)
- `GET /api/admin/supervisors` - список супервайзеров (только для owner/director)
- `POST /api/admin/users/{user_id}/assign-role` - назначение роли (только для owner)
- `DELETE /api/admin/directors/{director_id}` - удаление директора (только для owner)
- `DELETE /api/admin/supervisors/{supervisor_id}` - удаление супервайзера (только для owner/director)

## Обратная совместимость

### Что сохранено:
1. Legacy alias `get_admin_user()` - работает как `get_supervisor_user()`
2. Переменная `ADMIN_IDS` - все еще работает, назначает роль `supervisor`
3. Флаг `isAdmin` в authStore - работает для всех supervisor/director/owner
4. Все существующие endpoints работают с новыми ролями

### Что изменилось:
1. Роль `admin` больше не существует - все существующие `admin` пользователи автоматически становятся `supervisor`
2. Проверки ролей обновлены на новые роли
3. UI отображает новые названия ролей

## Проверка после миграции

### 1. Проверьте базу данных:
```sql
-- Проверьте, что нет пользователей с ролью 'admin'
SELECT COUNT(*) FROM users WHERE role = 'admin';
-- Должно вернуть 0

-- Проверьте распределение ролей
SELECT role, COUNT(*) FROM users GROUP BY role;
```

### 2. Проверьте конфигурацию:
- Убедитесь, что `OWNER_IDS` правильно настроен
- Проверьте, что после входа пользователь получает правильную роль

### 3. Проверьте функциональность:
- Owner может видеть всех менеджеров
- Owner может назначать директоров
- Director видит всех менеджеров
- Supervisor видит только менеджеров из своих групп

## Решение проблем

### Проблема: Пользователь не получает роль owner
**Решение:**
1. Проверьте `OWNER_IDS` в `.env` - должен содержать только цифры, без пробелов
2. Перезапустите API после изменения `.env`
3. Проверьте логи API - должно быть сообщение `[DEBUG] Setting user ... to owner role`
4. Если пользователь уже был создан с другой ролью, обновите вручную в БД или удалите и создайте заново

### Проблема: Пустой экран в списке менеджеров
**Решение:**
1. Проверьте роль пользователя - owner/director должны видеть всех менеджеров
2. Проверьте консоль браузера на наличие ошибок
3. Проверьте логи API - должно быть сообщение `[DEBUG] list_managers: ...`
4. Убедитесь, что в БД есть пользователи с `role = 'manager'` и `approval_status = 'approved'`

### Проблема: Ошибка при выполнении миграции
**Решение:**
1. Убедитесь, что миграция 019 выполнена перед миграцией 020
2. Проверьте, что нет активных транзакций
3. Выполните миграции вручную, если нужно

## Дополнительные заметки

- Роль в `user_group_membership` (admin/member) - это роль участия в группе, не роль пользователя. Она не изменилась.
- Все существующие функциональности работают с новыми ролями
- Система полностью обратно совместима - старые пользователи с ролью `admin` автоматически становятся `supervisor`
